# Segur Backend — Claude Code Instructions

> Any architectural change MUST be reflected back into both this file and `.github/copilot-instructions.md`.

## Tech Stack

- **Runtime**: Bun (NOT Node.js)
- **Framework**: ElysiaJS `1.4.26`
- **Validation**: Zod `3.25.36` via Elysia's Standard Schema. Do NOT use `Elysia.t` / TypeBox.
- **OpenAPI**: `@elysiajs/openapi` with Scalar UI at `/openapi`
- **Database**: PostgreSQL + Prisma ORM `7.4.1` (Rust-free engine, `prisma-client` generator, `@prisma/adapter-pg`)
- **JWT**: `jose 6.2.0` (direct dependency). Do NOT use `@elysiajs/jwt`.
- **Email**: Resend HTTP API called with plain `fetch`. Do NOT install the `resend` SDK.
- **Email templates**: React Email (`@react-email/components 1.0.12` + `@react-email/render 2.1.0`, `react 19.2.8`). `.tsx` files under `src/shared/infrastructure/emails/`.
- **Testing**: `bun test` (Bun's native test runner)
- **Linting/Formatting**: Biome `2.4.4`

## Strict Rules

### Dependencies
- ALL dependencies MUST use exact versions. Use `bun add --exact` / `bun add -d --exact`.
- TypeScript is pinned to `5.9.3`.

### Imports
- NEVER use `.js` extensions on imports — Bun resolves TypeScript natively.
- `@/` → `src/` (e.g. `import { envConfig } from '@/config/env'`)
- `@gen/` → `generated/prisma/` (e.g. `import { UserRole } from '@gen/enums'`)
- Relative imports only within the same module folder.

### No Barrel Exports
- NEVER create `index.ts` barrel/re-export files. Biome enforces `noBarrelFile: error`.
- Always import directly from the specific file.

### Elysia Plugin Naming
All Elysia instances MUST use: `@app/[module]/[name]`
- Examples: `@app/config/db`, `@app/modules/health`, `@app/shared/response`

### Error Handler
- `errorHandler` (`src/shared/middleware/error-handler.ts`) MUST register its `onError` with `{ as: 'global' }`. Elysia plugin hooks are **local** by default: without it the handler never runs, and every `AppError` (401/403/404) is returned as raw text with status 500.
- Being global, the hook also receives Elysia's built-in errors (`NOT_FOUND`, `VALIDATION`, `PARSE`). Their status codes MUST be preserved — never collapse them into 500.
- `tests/e2e/error-shape.test.ts` locks both behaviors in.

### Response Shape
ALL endpoints MUST return `ApiResponse<T>`:
```ts
{ data?: T, success: boolean, message?: string, meta?: { pagination?: PaginationInfo } }
```
Use response helpers from context: `jsonOk(data)`, `jsonOk(data, message)`, `jsonOk(page)` (auto-builds `meta.pagination` from a `Page<T>`), `jsonOkNoData(message)`, `jsonError(code, message)`. NEVER return raw objects. NEVER assemble pagination metadata by hand.

### Validation — No Double Parsing
- Pass Zod schemas to Elysia route options (`{ body: loginSchema }`). Elysia validates automatically.
- NEVER call `.parse()` / `.safeParse()` inside handlers. Data is already validated and typed.

### Routers
- **`publicRouter`** (`src/shared/routers/public-router.ts`): `dbPlugin + errorHandler + responsePlugin + paginated macro`. For unauthenticated routes.
- **`authRouter`** (`src/shared/routers/auth-router.ts`): inherits `publicRouter + jwtServicePlugin`, resolves Bearer token → `userId`, `userRole`, `companyId`. Provides `withRole` and `requireCompany` macros. For protected routes.
- Both use `.as('scoped')`.
- Every module controller MUST `.use(publicRouter)` or `.use(authRouter)`.
- If a controller has both public and protected routes, split into two Elysia instances.
- Controllers MUST also `.use()` only the specific service plugins they need.

### Macros
- **`paginated`** (on `publicRouter`): set `{ paginated: true }` or `{ paginated: { sortFields: [...] } }` to resolve a `Pageable` instance into the handler context. Validates `?page`/`?pageSize`/`?sortField`/`?sortBy` from the query string via `pageableSchema`. The optional `sortFields` allow-list rejects unknown `sortField` values with `400 VALIDATION_ERROR`.
- **`withRole`** (on `authRouter`): `{ withRole: UserRole.MASTER_ADMIN }` or `{ withRole: ['OWNER', 'MASTER_ADMIN'] }`. Throws `ForbiddenError` (403) on mismatch.
- **`requireCompany`** (on `authRouter`): set `{ requireCompany: true }` on any tenant-scoped route. Throws `ForbiddenError` (403) if `companyId` is `null` (i.e. the caller is a `MASTER_ADMIN`). Also narrows `companyId` from `string | null` to `string` in the handler — no `as string` cast needed. Use on every route that requires a company-scoped account (`OWNER`, `AGENT`).

### Pagination
Spring-style pagination API used end-to-end (controller → service → repository).
- **`Pageable`** (`src/shared/domain/pagination.ts`): immutable value object holding `page`, `pageSize`, and optional `sort: readonly Sort[]`. Exposes `skip`, `take`, and `orderBy` (Prisma-shaped; defaults to `{ createdAt: 'desc' }` when no sort given). Construct with `new Pageable(...)` or `Pageable.of(page, pageSize, sort?)`.
- **`Page<T>`**: immutable result wrapper with `content: readonly T[]`, `total`, `page`, `pageSize`. Derived: `totalPages`, `hasNext`, `hasPrevious`, `isEmpty`. `.map(fn)` for projection. Build with `Page.of(content, total, pageable)` or `Page.empty(pageable)`.
- **Schema** (`src/shared/utils/pagination.ts`): `pageableSchema` validates `?page`, `?pageSize`, `?sortField`, `?sortBy=asc|desc`. Use `listQuery({...filters})` in module `schemas.ts` to compose pagination + per-resource filter Zod fields in one schema.
- **Macro**: `{ paginated: ... }` on a route resolves `pageable: Pageable` into the handler (see `### Macros`). NEVER call `toPageable()` manually inside a handler — the macro does it.
- **Response**: `jsonOk(page)` detects `Page<T>` via the overload and emits `{ data: content, meta: { pagination: {...} } }` automatically.

Repository signatures MUST be `findAll(pageable: Pageable, filters: XFilters): Promise<Page<X>>`. Use `pageable.skip`, `pageable.take`, `pageable.orderBy` directly with Prisma:
```ts
async findAll(pageable: Pageable, filters: XFilters): Promise<Page<X>> {
  const [data, total] = await Promise.all([
    this.prisma.x.findMany({ where, skip: pageable.skip, take: pageable.take, orderBy: pageable.orderBy }),
    this.prisma.x.count({ where }),
  ])
  return Page.of(data, total, pageable)
}
```
NEVER hand-compute `skip`/`take` or hardcode `orderBy: { createdAt: 'desc' }` — both come from `Pageable`. Services MUST also take `Pageable` and return `Page<T>` so the pagination type flows through all layers without translation.

### Dependency Injection
- Services with business logic MUST be classes implementing interfaces (ports). Dependencies injected via constructor.
- Anemic pass-through services (no logic) do NOT need interfaces yet.
- Interfaces → `shared/domain/` (cross-cutting) or `modules/[feature]/domain/`.
- Implementations → `shared/infrastructure/` or `modules/[feature]/infrastructure/`.
- ALL wiring happens in `src/config/services.ts`, which exports per-module Elysia plugins.
- NEVER instantiate services inside controllers. NEVER create a monolithic "all services" plugin.

### Cross-Module Boundaries
- Modules MUST NOT import from other modules' layers.
- If module A needs data owned by module B, define a port in `modules/A/domain/` and an adapter in `modules/A/infrastructure/`.
- Example already in place: `AuthUserProvider` interface + `PrismaAuthUserProvider` adapter in the `auth` module instead of importing from `user`.

### Prisma-Generated Types
- NEVER manually redeclare types that duplicate Prisma models or enums.
- Import enums from `@gen/enums`. Import model types from `@gen/models/ModelName`.
- Domain entity interfaces MUST use `Pick<ModelType, ...>` for field reuse.
- Service input types MUST use `Pick<ModelType, ...>` for Prisma-managed fields, adding non-Prisma fields via intersection (`& { password: string }`).

### Entity Conventions
- ALL domain entities MUST extend `BaseEntity` (`id, status, createdAt, updatedAt`).
- ALL Prisma models MUST include: `status ResourceStatus @default(ACTIVE)`, `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`.
- Use `@@map("table_name")` on every model (plural snake_case).

### Prisma Global Omit
- PrismaClient is configured with `omit: { user: { passwordHash: true } }`.
- Override at query level with `omit: { passwordHash: false }` only when the hash is explicitly needed (e.g. `AuthService.login`).
- The `User` domain entity does NOT include `passwordHash`.

### Soft Deletion
- By default, never perform real DELETE. ALL deletions MUST set `status = 'DELETED'`.
- Repository delete methods MUST be named `softDelete`.
- ALL read queries MUST filter by `status: ResourceStatus.ACTIVE` by default.
- Explicit exception: `ColumnaKanban` uses a `hardDelete` repository/service method and physical DELETE endpoint as requested; its foreign key uses `ON DELETE SET NULL` so related policies remain intact.
- Use `findFirst` with `status: 'ACTIVE'` instead of `findUnique` where applicable.

### Auth
- JWT: `jose` via `JwtService` interface + `JoseJwtService`. Access + refresh token pair.
- JWT payload: `sub` (userId), `role`, `companyId`.
- Password hashing: `Bun.password` via `PasswordHasher` interface + `BunPasswordHasher` (Argon2id).
- Auth resolution: `authRouter` uses `.resolve()` to verify Bearer token and attach `userId`, `userRole`, `companyId`.
- Role check: `withRole` macro on route options. No DB lookup — role trusted from JWT.
- `MASTER_ADMIN` users have `companyId = null` (platform-level).

### Password Reset
- Stateless: NO `password_reset_tokens` table. The token is a JWT signed with `JWT_SECRET`.
- Reset token claims: `sub` (userId), `typ: 'pwd_reset'`, `pwd` (SHA-256 fingerprint of the current `passwordHash`). The `typ` claim prevents an access/refresh token from being used as a reset token and vice versa.
- Single-use by construction: saving the new password changes the hash, so the fingerprint no longer matches and the token stops validating. No cleanup job needed.
- The token does NOT carry `companyId` — `sub` already identifies one user in one company. Since the same email can exist in several companies, `POST /auth/forgot-password` sends ONE email per matching active account, each with its own token.
- `POST /auth/forgot-password` ALWAYS returns the same 200 response whether or not the email exists (no account enumeration).
- `EmailSender` port lives in `shared/domain/email-sender.ts`; `ResendEmailSender` renders the React Email template and POSTs to the Resend API. Application layer never touches HTML or React.

### Siniestros
- `clienteUserId` is ALWAYS derived from the poliza inside `SiniestroService.create` — never accepted from the request body. The client of a claim is whoever owns the policy.
- `creadoPorUserId` comes from the JWT (`userId`), not from the body.
- `fechaEvento` MUST fall inside the poliza coverage window (`fechaInicio..fechaVencimiento`) and MUST NOT be in the future. Relaxing this is a business decision, not a bug fix.
- `companyId`, `polizaId` and `clienteUserId` are immutable after creation (they are not part of `UpdateSiniestroInput`).
- CLIENT is read-only and only reaches siniestros linked to their own polizas.

### Archivos de Poliza
- The DB stores ONLY metadata (`nombre`, `mimeType`, `url`, `tamanoBytes`). Binaries NEVER touch the database: upload to the storage provider first, then POST the resulting `url`.
- The allowed `mimeType` list lives in `ArchivoPolizaService` (application layer), NOT in the Zod schema, so the rule has a single owner.
- Every operation is scoped through the poliza: `assertPolizaAccessible` resolves the poliza by `companyId` (and by `clienteUserId` when the caller is a CLIENT) and throws `NotFoundError` — never `ForbiddenError` — so a foreign poliza is indistinguishable from a missing one.
- Routes are nested as `/polizas/:id/archivos/:archivoId`. The poliza segment MUST stay named `:id`: Elysia's router requires the same parameter name at the same position, and `polizaController` already registers `/polizas/:id`.

### Multi-Tenant Model
- All data queries in tenant-scoped modules MUST be filtered by `companyId`.
- Same email can exist in multiple companies (`@@unique([companyId, email])`).
- Login flow: `POST /auth/identify` (email → list of companies) → `POST /auth/login` (email + password + companyId? → tokens).

## Architecture: Clean Architecture (Feature-First)

Dependencies point inward: Domain ← Application ← Infrastructure ← Presentation.

- **`domain/`** — entities, repository interfaces, service interfaces. NO framework imports.
- **`application/`** — service classes (use cases). Depends ONLY on domain. NO Elysia, NO Prisma, NO Zod.
- **`infrastructure/`** — Prisma repository implementations.
- **`presentation/`** — Elysia controllers (thin: destructure → call service → return helper) + Zod schemas.

Business logic MUST live in `application/`. If you write an `if` with business meaning in a controller, move it to the service.

## Testing

### Principles
- Unit tests (services) > E2E tests (critical paths) > Integration tests (repos).
- Every new service with business logic MUST have unit tests.
- Services are testable with plain mocks — no HTTP, no DB, no framework.

### Unit Tests (`tests/unit/`)
File structure mirrors source: `tests/unit/modules/[feature]/service.test.ts`

```ts
import { describe, it, expect, mock, beforeEach } from 'bun:test'

const mockRepo: MyRepository = {
  findById: mock(() => Promise.resolve(null)),
  // all interface methods
}
const service = new MyService(mockRepo)

// Cast for per-test stubbing:
(mockRepo.findById as ReturnType<typeof mock>).mockResolvedValue(entity)
```

### Integration Tests (`tests/integration/`)
Test Prisma repositories against a real Docker PostgreSQL.

### E2E Tests (`tests/e2e/`)
Test full request cycle via `app.handle(new Request(...))`. Keep to critical smoke tests.
